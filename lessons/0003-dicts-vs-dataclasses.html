Dicts vs Dataclasses

JS gives you one tool for structured data. Python gives you two — and the boundary between them is where JSON enters your program.

The mental model

You've already collided with this ('User' object is not subscriptable), so here's the full map:

The decision test from chat, worth memorizing: do you know the field names while writing the code? Yes → dataclass. No (they arrive at runtime) → dict.

Safe access: .get() and KeyError

A dict read of a missing key doesn't hand you undefined — it raises:

d = {"name": "Ben"}
d["role"]                  # KeyError: 'role'  — loud, at the exact line
d.get("role")              # None              — your ?. equivalent
d.get("role", "user")      # "user"            — your ?? with a default
"role" in d                # False             — check before you leap

Python's culture prefers the loud version: if the key should exist, use brackets and let the KeyError find your bug early. Reach for .get() only when absence is a legitimate case you're handling — exactly the discipline ?. demands in JS.

Where dicts are forced on you: JSON

The standard library's json module is JSON.parse/JSON.stringify with different names:

JavaScript

const data = JSON.parse(text);
const text2 = JSON.stringify(data);

Python

import json
data = json.loads(text)   # "load string"
text2 = json.dumps(data)  # "dump string"

json.loads can only give you dicts, lists, and primitives — it has no idea your domain has Users. So real programs have a boundary: dicts on the outside (wire format), dataclasses on the inside (your logic). The crossing:

d = {"name": "Ben", "role": "admin", "active": True}
user = User(**d)    # ** spreads the dict into keyword args — User(name="Ben", role="admin", active=True)

**d is the spread operator for calls, like JS fn(...obj) — it unpacks each key as a keyword argument. (Functions get a whole lesson soon; for now, ** = "spread this dict into the call.")

Defaults for missing fields

If a dict is missing a field, User(**d) fails at construction. The dataclass-side fix — declare a default, exactly like a TS optional-with-default:

@dataclass
class User:
    name: str
    active: bool
    role: str = "user"   # defaulted fields go last

Now User(**{"name": "Ada", "active": True}) works, and every missing role uniformly becomes "user" — one declaration instead of .get() calls scattered everywhere.

Hands on: cross the boundary

Predict-first, as usual. In main.py, start from raw JSON — note the deliberately missing role:

import json

raw = '[{"name": "Ben", "role": "admin", "active": true},
        {"name": "Ada", "active": true},
        {"name": "Sam", "role": "admin", "active": false}]'
data = json.loads(raw)   # (put the string on one line in your file)
  1. Predict, then run: print(data[1]["role"]). Read the full traceback bottom-up before fixing anything — this one's on purpose.
  2. Fix it with .get() so Ada prints user.
  3. Add role: str = "user" to your User dataclass, then cross the boundary with a comprehension: users = [User(**d) for d in data]. Print each user's name and role via dot access.
  4. Victory check: {u.role for u in users} should print {'admin', 'user'} (either order — you know why).

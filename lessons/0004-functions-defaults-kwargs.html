Functions: Defaults, Keywords, and the Spread Remap

Python functions look like JS functions with different punctuation — until default values and keyword arguments change how APIs are designed. Plus the gotcha that bites every JS developer exactly once.

Keyword arguments: the options-object killer

In JS, a function with many optional settings takes an options object. Python doesn't need that pattern — any parameter can be passed by name at the call site:

JavaScript

fetchData(url, {
  retries: 3,
  timeout: 30,
});

Python

fetch_data(url, retries=3, timeout=30)

def fetch_data(url, retries=1, timeout=10):
    ...

No wrapper object, no destructuring on the receiving end. Idiomatic Python calls pass anything non-obvious by keyword — send(msg, urgent=True) reads better than send(msg, True), and reviewers will expect it.

You can even force it: parameters declared after a bare * are keyword-only. def send(msg, *, urgent=False) makes send(msg, True) an error — the call site must say urgent=True. You'll see this constantly in library signatures (FastAPI included).

The gotcha: defaults are evaluated once

In JS, a default value expression re-runs on every call. In Python it runs once, when def executes — and the result is shared by all calls. With immutable defaults (1, "user", None) you'll never notice. With a mutable default, you get Python's most famous trap:

def add_tag(tag, tags=[]):   # ⚠️ one shared list, created at def time
    tags.append(tag)
    return tags

add_tag("a")   # ['a']
add_tag("b")   # ['a', 'b']  ← same list! JS would give ['b']

The idiom every Python codebase uses — default to None, create inside:

def add_tag(tag, tags=None):
    if tags is None:
        tags = []          # fresh list per call, like JS defaults
    tags.append(tag)
    return tags

Linters flag def f(x=[]) and def f(x={}) on sight. Now you know why.

*args and **kwargs: the full spread story

You met User(**d) in lesson 3 — spreading a dict into a call. The same stars work on the receiving side, like JS rest parameters:

JavaScript

function log(...values) { ... }

// no real equivalent — closest is
// an options object catch-all

Python

def log(*values):     # extra positional args → tuple
    ...

def tag(**attrs):     # extra keyword args → dict
    ...

So the stars are one symmetric system — one star for positional, two for keyword; gather in a signature, spread in a call:

def tag(name, **attrs):                    # gather:  attrs = {"href": "/", "cls": "nav"}
    parts = [f'{k}="{v}"' for k, v in attrs.items()]
    return f"<{name} {' '.join(parts)}>"

tag("a", href="/", cls="nav")              # '<a href="/" cls="nav">'

opts = {"href": "/", "cls": "nav"}
tag("a", **opts)                           # spread: same call, dict source

The conventional names args/kwargs ("keyword args") are just convention — the stars do the work. You'll meet **kwargs everywhere in FastAPI and the AI SDKs: client.messages.create(model=..., max_tokens=..., **extra).

Gotcha

lambda is not an arrow function. It's restricted to a single expression — no statements, no blocks. The moment you want two lines, write a def. Python culture prefers named functions anyway; a lambda assigned to a variable is a lint error (PEP 8).
